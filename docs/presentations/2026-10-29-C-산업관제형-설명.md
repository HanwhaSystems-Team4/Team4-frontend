# C 산업 관제형 · D 페이지 수정 — 원래 화면과 무엇을 왜 바꿨나

팀 회의(2026-10-29) 설명용 기록. A(현재 버전) · E(조장님 원본)와 C(산업 관제형), 그리고 C를 이어받은 D(페이지 수정)를 나란히 놓고 비교한다.
자세한 결정 과정은 [0007](../decisions/0007-AB-테스트-후보-재구성과-산업-관제형.md) · [0008](../decisions/0008-홈-설비-표와-정렬.md) · [0009](../decisions/0009-C-홈-알람-통합-표와-라이트-다크.md) · [0010](../decisions/0010-D-페이지-수정.md)에 있다.

## 한 줄 요약

> **C**: 정비사가 홈에서 **어떤 알람부터 볼지 한눈에 판단**하게 하고, 알람과 보고서를 **한 표로 합쳐 색으로 구분**했다.
> **D**: C를 그대로 이어받고, 점검할 때 **왼쪽의 센서 값으로 AI(LLM)의 판단이 맞는지 확인**하도록 진단 화면을 3열로 만들고 **점검과 조치를 한 단계로** 합쳤다.
> 둘 다 화면 이동 순서와 API는 그대로이고, 보이는 방식만 바꿨다.

## D: C에서 다시 바꾼 것 (C → D)

D는 C의 모든 것(색 · 라이트/다크 · 홈 표 · 문구 · 화면 크기)을 그대로 쓰고, 아래 세 가지만 다르다.

| 화면 | C | D 페이지 수정 | 왜 |
| --- | --- | --- | --- |
| 진단 화면 | 2칸: 원인 순위 + 유사 기록 / 다음 점검 | **3칸: 센서 값 / 원인 순위 + 유사 기록 / 다음 점검** | 점검할 때 **왼쪽에 센서 데이터가 있으면 LLM(AI)의 판단이 맞는지 확인하기 더 쉽다.** 센서 값 → 원인 순위 → 다음 점검을 왼쪽에서 오른쪽으로 읽는다. 범위 밖 센서는 빨강 |
| 진행 단계 | 알람 · 진단 · 점검 · 조치 · 보고서 5칸 | **센서 확인 · 진단 · 점검·조치 · 보고서 4칸** | 점검과 조치를 한 흐름으로 본다. 조치 중에도 "점검 · 조치" 칸이 현재 단계. 지난 화면은 점검과 조치 기록을 이어서(이전 · 다음) 본다 |
| 알람 단계 이름 | "알람" | **"센서 확인"** | 이 화면에는 센서 값이 있고 무엇이 정상 범위를 벗어났는지 확인하는 곳이라 이름을 실제 화면에 맞췄다. 상단 빨간 ALARM 띠와 홈의 알람 상태는 알람 자체를 가리키므로 그대로 |

D의 센서 패널은 서버가 알람 화면에 주는 값(이름 · 값 · 평소 범위 · 상태)을 그대로 보인다. 화면에서 판정을 만들지 않는다.

## 바꾸지 않은 것

- 화면 이동 순서(어떤 버튼을 누르면 어떤 화면이 나오는지)
- API 호출과 서버가 주는 값(화면은 받은 값만 보여 준다). D의 4단계도 화면 칸만 합친 것이고 서버의 단계 구분은 그대로다
- 등급 배지 색의 의미(A 초록 · B 파랑 · C 주황 · D 빨강)
- A · B · E 화면, 그리고 D를 만들 때 C 화면(비교를 위해 후보별로 필요한 것만 바꿨다)

## 함께 고치며 알게 된 것

- **"3건 중 상위 3건"으로 보이던 오류:** 지난 화면(진단)에는 알람 정보가 같이 오지 않아 전체 건수 n을 카드 수로 대신 쓰고 있었다. 알람 단계 기록에서 n(서버는 세션마다 유사 기록 10건을 저장)을 가져오도록 고쳤다. 서버 문제가 아니었다.
- **M-12의 "센서 2개"가 표에는 1개만 보이던 이유:** 서버는 알람 경계가 있는 센서 4개(기계 출력 · 온도 차 · 토크 · 공구 마모)를 모두 세는데 알람 표는 5행만 보여 준다. M-12는 기계 출력 알람이고 온도 차 8.0 K도 경계 8.3 K 아래인데 표에 온도 차 행이 없다. C · D는 "안정 범위 밖 2개 · 표에 없는 1개 포함"으로 설명한다. 서버의 세는 규칙은 바꾸지 않았다.
- **비교 발표 규칙:** 비교를 위해 후보마다 필요한 부분만 바꾸고 나머지는 그대로 둔다. 공통 화면 코드에 후보용 요소를 더할 때는 다른 후보에서 숨겨 지금 화면과 똑같이 보이게 한다.

## 지금 한계와 백엔드에 요청할 것

| 한계 | 이유 | 요청 |
| --- | --- | --- |
| 비슷한 과거 기록 **상위 3건만** 보이고 나머지 7건은 건수만 보임 | 서버가 상위 건들만 내려 준다(세션 응답에 상위 3건 카드와 찾은 건수만 있음) | 세션 응답에 **유사 기록 목록**(전체 + 유사도). 생기면 전체를 보이고 상위 10건을 강조할 수 있다 |

| 시안의 담당자 열 | API에 담당자가 없다 | 담당자 값 |
| D의 센서 패널에 막대(평소 범위 안 위치)는 없음 | 평소 범위가 "1,305 ~ 1,979" 같은 글로만 온다 | 범위를 숫자(하한 · 상한)로 |
| D의 4단계는 화면에서만 합침 | 서버는 점검 · 조치를 따로 센다 | D가 선택되면 서버 · 지난 화면 응답까지 합칠지 정한다 |

## 예상 질문과 답

- **왜 홈에 센서 값을 넣었나요?** 알람 화면에 들어가기 전에 값의 상태로 우선순위를 고르게 하려고요. 알람을 낸 센서는 빨강이라 바로 보여요.
- **알람과 보고서를 합치면 헷갈리지 않나요?** 상태 열(작성 바람 / 승인 대기 …)과 행 색이 다르고, 승인까지 끝난 건 반투명이에요.
- **"작성 바람"은 무슨 뜻인가요?** 아직 내가 점검하고 보고서를 써야 하는 알람(새 알람과 점검 중)이에요. 보고서를 확정하면 "승인 대기"로 바뀌어요.
- **왜 다크 모드가 되나요?** 야간 교대(22:00 ~ 06:00)가 주 사용 시간이라서요. 라이트(흰색)와 다크를 모두 가져요.
- **왜 안전 수칙을 뺐나요?** 점검 전에 잠금 화면에서 먼저 확인시키고 있어서 홈에서는 중복이에요.
- **"10건 중 상위 3건"인데 왜 3건만 보이나요?** 서버가 상위 3건 카드만 줘요. 나머지는 건수만 보이고, 전체를 보이려면 백엔드 변경이 필요해요.
- **D는 왜 진단 화면을 3열로 했나요?** 점검 전에 AI가 고른 원인 순위가 센서 값과 맞는지 바로 대조하려고요. 센서 값이 왼쪽에 있으면 판단을 검증하기 쉬워요.
- **점검과 조치를 왜 합쳤나요?** 정비사에게는 점검하다가 바로 조치로 이어지는 한 흐름이라서요. D는 칸만 합쳤고, 서버 기록은 그대로 두 단계예요.
- **"센서 확인"은 왜 그 이름인가요?** 그 화면은 센서 값을 보고 무엇이 정상 범위를 벗어났는지 확인하는 곳이라서요. "알람"은 상단 빨간 띠와 홈에서 그대로 알람을 뜻해요.
- **이것을 실제 서비스에 바로 쓰나요?** 아니요. 지금은 비교용 후보예요. 하나를 고르면 평소 디자인으로 옮기는 결정 기록을 새로 써요.

## 데모 방법

1. 레포 루트의 `AB테스트_실행.bat`을 더블클릭한다(백엔드 → 화면 → 브라우저).
2. 화면 위 막대에서 **A · B · C · D**를 바꿔 보고, **E 조장님 원본**은 새 탭으로 연다. 주소로는 `?v=c`, `?v=d`.
3. 라이트와 다크는 화면 위쪽의 '다크' 버튼(또는 주소 `?theme=dark`). C · D의 기본은 흰색 라이트.
4. 정비자 앱 아이디 `tech.kim` 등, 파트장 앱 아이디 `lead.park`. 비밀번호는 백엔드 `.env`에 있다. 알람은 `AB테스트_알람만들기.bat`으로 더 만든다(담당자에 배정되므로 해당 정비자로 로그인).
5. 백엔드 없이 화면만 비교: `http://localhost:5181/preview.html`(D는 `&v=d`).
