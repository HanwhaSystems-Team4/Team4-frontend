# 0004. A/B 테스트용 디자인 후보 3개를 전환식으로 둔다

- 상태: 제안
- 날짜: 2026-10-23
- 작성: 문선웅
- 관련: [0003](0003-디자인-변경-범위를-색·테두리·글꼴로-한정.md)(평소 디자인 범위), `packages/ui/src/styles/variants/`, `AB테스트_실행.bat`

## 배경

팀원 대상 A/B 테스트에서 지금 화면(A)과 새 후보 3개(B · C · D)를 나란히 보여 주고, 왜 그렇게 바꿨는지 발표한다.
이번 테스트에서는 버튼 크기 · 색 · 모양 · 위치까지 바꿔도 되지만 **화면 순서(어떤 버튼을 누르면 어떤 화면이 나오는지)는 그대로** 지켜야 한다.
또 테스트한 사람들 의견으로 **페이지 전체가 스크롤되지 않고 태블릿처럼 보여야** 한다.

0003은 평소 디자인 변경을 색 · 테두리 · 글꼴로 한정했다. 이 기록은 그 규칙을 바꾸지 않고, 테스트 모드에서만 켜지는 후보를 따로 둔다.

## 후보 만드는 방식

| | 1. 후보마다 브랜치 | 2. 후보마다 컴포넌트를 새로 작성 | 3. CSS 덧씌우기 + 전환 막대 |
| --- | --- | --- | --- |
| 하는 일 | 브랜치 4개를 오가며 서버를 다시 켬 | 화면 코드를 후보별로 복사해 고침 | 같은 화면(DOM)에 `html[data-variant]`별 CSS만 다르게 |
| 화면 순서 보장 | 브랜치마다 따로 확인 | 코드가 갈라져 어긋날 수 있음 | 화면 코드가 하나라 자동으로 같음 |
| 테스트 진행 | 후보마다 서버 재시작 | 한 번에 가능 | 화면 위 막대에서 바로 전환 |
| 원래 버전 영향 | 없음 | 화면 코드가 늘어남 | 없음(테스트 모드가 아니면 후보 CSS가 걸리지 않음) |

**3을 고른다.** 화면 순서를 지키라는 조건을 코드 구조로 보장하고, 테스트 중에 한 화면에서 A ~ D를 바로 바꿔 볼 수 있다.

### 바꾼 이유(발표용 요약)

- **B 현장 터치형**: 정비자는 장갑을 끼고 한 손에 공구를 든 채 태블릿을 누른다. 그래서 누르는 것은 모두 48px 이상, 가장 자주 누르는 진행 표시는 엄지가 닿는 아래로 내렸다. ISA-101처럼 바탕은 회색으로 가라앉히고 색은 알람(빨강) · 결과(초록 · 빨강) · 지금 할 일(파랑)에만 썼다. 결과 버튼은 고르면 색으로 꽉 채워 멀리서도 무엇을 골랐는지 보인다.
- **C 업무 도구형**: 매일 쓰는 사람에게는 "지금 어디까지 왔나"가 항상 같은 자리에 있어야 한다. 진행 단계를 왼쪽 세로 목록으로 고정하고(Atlassian 진행 표시 세로형), 상단을 Carbon UI Shell처럼 검은 막대로 만들어 본문과 분리했다. 파트장 앱은 메뉴가 4개뿐이라 왼쪽 메뉴 대신 위쪽 탭으로 옮겨 표를 화면 폭 전체로 넓혔다.
- **D 플로팅 벤토형**: 이 서비스의 핵심은 "AI Agent가 고른 다음 행동"이다. 그래서 다음 점검 카드를 보라 그라데이션 **주인공 카드**로 만들고 AI 해석은 Apple Intelligence처럼 그라데이션 테두리로 빛나게 해, 화면에서 AI가 낸 판단이 가장 먼저 보이게 했다. 나머지 정보는 Apple 제품 페이지의 벤토 그리드처럼 크기가 다른 둥근 타일로 나눴다. 지금 처리 중인 알람은 iOS Dynamic Island처럼 **상단 가운데 검은 알약**에, 진행 단계는 macOS Dock처럼 **아래에 떠 있는 독**에 두어 본문을 넓히고 "지금 무엇을 · 어디까지"를 화면 위아래 끝에서 바로 읽게 했다. 파트장 앱은 Arc 브라우저처럼 떠 있는 둥근 사이드바를 썼다.
- (처음 만든 D 야간 관제형은 사용자 의견에 따라 후보에서 빼고, 어두운 화면은 모든 후보에서 고를 수 있는 **다크 모드 기능**으로 바꿨다 → [0005](0005-다크-모드-기능.md))

### E. 조장님 레포 원본(비교 기준)

백엔드 레포(c1a15-maint-guide)의 `apps/tech` · `apps/lead`를 그대로 빌드해 docker compose의 nginx가 띄운 화면(정비자 `127.0.0.1:8081`, 파트장 `:8082`)이다. 이 레포의 A는 그 화면을 옮겨 와 색 · 테두리 · 글꼴만 바꾼 것(0003)이라, E는 A ~ D 모두의 출발점이다. 코드를 복사하지 않고 원래 빌드를 그대로 보여 주도록 전환 막대에서 새 탭으로 연다. 다른 주소라 로그인은 따로 한다.

### 네 후보 공통

- 화면 · 버튼 · 이동 순서(DOM과 클래스)는 같다. 바뀌는 것은 CSS뿐이다. 화면 테스트 85개가 그대로 통과한다.
- 태블릿처럼: 화면 틀(정비자 1080 × 740, 파트장 1280 × 620)을 창 크기에 맞춰 통째로 확대 · 축소하고 페이지 전체 스크롤은 없앤다. 넘치는 내용은 틀 안에서만 스크롤된다(A도 같은 방식이라 비교가 공평하다).
- 등급 배지 색의 의미(A 초록 · B 파랑 · C 주황 · D 빨강)는 바꾸지 않는다.

- 변경: 두 앱 `main.tsx`가 `variants.css`를 불러오고, `VITE_AB_TEST=1`일 때만 전환 막대를 붙인다. 평소 `npm run dev:*` · 빌드 화면은 그대로다.
- 백엔드 레포(c1a15-maint-guide)는 고치지 않는다. bat은 이미 만든 백엔드가 있으면 init을 건너뛰고(`docker compose up -d --no-deps api web`) 켠다.

## 다시 검토할 조건

- A/B 테스트 결과로 한 후보를 고르면, 그 후보의 CSS를 `theme.css`(색) · 배치 파일로 옮기는 새 결정 기록을 쓰고 0003을 대체할지 정한다.
- 화면 구조(DOM)를 바꿔야 하는 후보가 나오면 이 방식(CSS만)으로는 안 되므로 다시 본다.
